## Working rules retained

Robert decides; agents propose. Ask one question at a time and wait. Explain options, real alternatives and tradeoffs plainly, with a recommendation; technical claims need proposed experiments and evidence, not votes between models. Say what every decision number means. Robert does not read code: reports must show readable promises, examples and results. Small steps, big picture first. Every task has a written stop condition.

No self-certification: the code author may not write/change its acceptance checks. Acceptance is approved beforehand, then locked; preserve hashes, clean rebuilds, kernel assumptions and required broken-copy controls. Never retune expected outputs. Do not move anything from v1 without approval or add process machinery merely because an agent prefers it. Tools are selected for each experiment; Koka/Rust are not defaults.

Current work happens here in Codex under Robert’s instruction (D108). Model agreement is not independent evidence, and agents do not gain general Mo design authority. [ROB-1132](https://linear.app/robert-guss/issue/ROB-1132/resolve-phase-2-builder-and-acceptance-workflow-arrangement) and its Builder/Tester arrangement are historical completed-trial records. Preserve existing scientific proof/check boundaries; the retired workflow is not a reason to dispatch external agents.

The exact standing rules and historical context remain in the [pre-migration CLAUDE.md](<https://github.com/robertguss/mo-v2/blob/13ca4c99334c3c6fa0ac157a6a5165b0882d7eb4/CLAUDE.md>); its repository status/decision-log locations were superseded by the Linear migration, and its Amp/Herdr operational requirements are superseded by D108. ## Linear status mapping

Ready: approved unblocked executable issue. Planning: brief/acceptance preparation. Building: implementation active. In Review: candidate awaiting review/merge. Needs Input: blocked on decision. Backlog: deferred or unapproved. Done: confirmed merged delivery, never “agent says complete.” Historical experiment completion is in the catalog rather than invented delivery events.

Delivery defaults to dedicated branch push; no new PR, merge, deployment or release authorization is implied. Read issue description/comments before work and before updates; avoid duplicate records. Stop on a real new decision, spec conflict, failed acceptance or unexpected branch movement.
